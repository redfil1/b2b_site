## Зона ответственности (разделение с чатом "Заявка")

- **Этот чат ("Архитектура и Backend")**: маршрут API, контракт запроса/ответа, серверная логика обработки заявки, стратегия генерации КП.
- **Чат "Заявка"**: состав полей формы на клиенте, клиентская валидация, UI-состояния (загрузка/ошибка/успех).

Зафиксировано впервые в этом документе — раньше генерация КП числилась полностью за чатом "Заявка" без разделения на клиент/сервер; после обновления инструкций серверная часть перенесена сюда.

## Зафиксировано

- Единственный route handler для приёма формы заявки: `app/api/request/route.ts`, метод `POST`.
- Без отдельного бэкенда — вся обработка внутри route handler'ов Next.js и нативных примитивов Vercel.
- Ошибки — обычный try/catch, ответ с понятным сообщением для пользователя (см. `Coding Rules.md`).
- Комментарии обязательны на: (1) валидации входных данных, (2) шаге генерации КП, (3) шаге загрузки файла в хранилище.
- **Контракт `RequestPayload`** — зафиксирован в `CommercialOffer.md`, раздел 6 (чат "Заявка"). Тип объявляется один раз в `types/request.ts` и импортируется и в форму, и в `app/api/request/route.ts`. Сводка полей:
  - `companyName`, `inn`, `contactName` — строки, обязательны;
  - `phone?`, `email?` — хотя бы одно из двух обязательно (кросс-полевая проверка на сервере и клиенте);
  - `product: { slug?: string; title: string }` — `slug`, если заявка со страницы товара, `title` — всегда;
  - `comment?` — опционально.

### Флоу заявки → КП (асинхронный)

1. **`POST /api/request`** — принимает `RequestPayload` (состав полей — чат "Заявка"), валидирует, сразу отправляет уведомление менеджеру (email с сырыми данными заявки — не ждёт PDF, чтобы лид не терялся, если генерация КП затормозит или упадёт), запускает генерацию PDF в фоне через `after()` (Next.js) и **сразу** отвечает клиенту `{ requestId }`. Клиент переходит на `/request/success?id={requestId}`.
2. **Генерация PDF** (фоновая часть того же вызова, через `after()`): рендерит КП компонентами `@react-pdf/renderer` по шаблону в `lib/pdf/`, загружает готовый файл в **Vercel Blob** (`@vercel/blob`) по пути вида `kp/{requestId}.pdf`.
3. **`GET /api/request/[id]/status`** — проверяет, есть ли blob `kp/{requestId}.pdf` (через `head()` из `@vercel/blob`). Если есть — `{ status: 'ready', downloadUrl }`; если нет — `{ status: 'generating' }`.
4. Страница `/request/success` поллит `status` каждые несколько секунд, показывает "КП формируется..." → ссылку на скачивание, когда готово.

**Почему без отдельной БД/очереди**: статус генерации не хранится отдельно — сам факт наличия файла в Blob-хранилище и есть статус. Это укладывается в правило "не заводить абстракции без необходимости": не нужен ни воркер, ни таблица статусов, только один нативный примитив Vercel (Blob storage), который уже и так в экосистеме деплоя.

**Если PDF не сгенерировался** (ошибка внутри `after()`): клиент увидит "generating" бесконечно на клиенте — это сознательный компромисс на первую версию, т.к. лид всё равно долетел до менеджера письмом на шаге 1. При необходимости таймаут на клиенте (например, через 60 сек показывать "мы свяжемся с вами письмом") — деталь для чата "Заявка"/"Фронт", не блокирует эту архитектуру.
