# Product.md — структура карточки товара

Статус: **черновик схемы полей**, актуализирован по итогам проверки на противоречия
(3 пункта из Frontend.md, раздел 6, закрыты ниже). Реальных товаров в этом чате пока
не обработано — поставщик ещё не прислал прайс-листы/спецификации. Документ фиксирует
*структуру*, которой будут соответствовать все будущие карточки.

Источник истины для типа `Product` — этот документ. Реализация — в `types/product.ts`
(`Product` — публичный тип, `ProductDraft` — служебное расширение, см. раздел 4),
карточки-данные — в `lib/data/products.ts`.

## 1. Поля карточки товара (публичный тип `Product`)

| Поле | Обязательность | Тип (ориентир для `types/product.ts`) | Описание |
|---|---|---|---|
| `id` | обязательно | `string` | Уникальный идентификатор товара |
| `slug` | обязательно | `string` | Часть URL `/catalog/[category]/[slug]` |
| `title` | обязательно | `string` | Название, адаптированное для русскоязычного B2B-клиента (не дословный перевод из прайса) |
| `manufacturer` | обязательно, если известен* | `string` (ключ на `lib/data/manufacturers.ts`) | Производитель |
| `model` | обязательно, если известна* | `string` | Модель/артикул производителя как в прайсе, без адаптации (в отличие от `title`) |
| `country` | обязательно, если известна* | `string` | Страна производства/происхождения |
| `sku` | опционально | `string` | Артикул/код товара у поставщика — не у всех позиций есть |
| `category` | обязательно | `string` (ключ категории) | Категория товара, участвует в URL `/catalog/[category]` |
| `specs` | обязательно, может быть неполным | `{ label: string; value: string }[]` | Технические характеристики — таблица «параметр / значение». Только то, что подтверждено поставщиком |
| `package` | опционально | `string[]` | Комплектация — список того, что входит в поставку (вкладка «Комплектация») |
| `documents` | опционально | `{ title: string; url: string }[]` | Документы: PDF-паспорт оборудования, сертификаты и т.п. Ссылки — на Vercel Blob (см. `Tech_Stack.md`, путь `docs/{productId}/{filename}.pdf`) |
| `description` | обязательно | `string` (2–4 предложения) | Что за техника/оборудование, для каких задач применяется |
| `deliveryTime` | обязательно | `string` | Срок поставки, если известен, иначе `"уточняется по заявке"` |
| `availability` | обязательно | `'available' \| 'unavailable'` | См. раздел 2.2 — не о складе в РФ, а о том, продаёт ли поставщик позицию сейчас |
| `images` | опционально | `string[]` | Пути к изображениям (`public/` или внешний домен через `next.config.js`) |

> **Поле `featured` удалено (2026-09-01).** Партнёры решили убрать блок «Популярные
> товары» с сайта. Флаг больше не входит в тип `Product`, убран из тестовых данных
> и с главной. Подробнее — раздел 2.4.

\* Если данных нет у поставщика — поле не заполняется произвольно, а уходит в `missingData` (см. раздел 4).

## 2. Правила заполнения

### 2.1 Общие
- **Никаких выдуманных характеристик.** В карточку попадает только то, что явно есть в материалах поставщика.
- **Если данных не хватает** — поле помечается в `missingData` с явной формулировкой, что нужно запросить у поставщика, а не заполняется предположением.
- **Название** (`title`) формулируется для русскоязычного B2B-покупателя, но без искажения модели/технических фактов. `model` при этом хранится отдельно и без адаптации — так у карточки остаётся точная ссылка на позицию у поставщика.
- **Описание** — 2–4 предложения, только на основе исходных материалов.
- **Срок поставки** — если поставщик не указал, ставится ровно строка `"уточняется по заявке"`.
- **Категория** — обязательна всегда, без неё карточка не считается готовой.

### 2.2 Наличие (`availability`) — решение противоречия 6.3

Склада в РФ нет, все товары идут под заказ из Китая (и шире — от разных поставщиков,
см. раздел 2.3). Поэтому классический бейдж «в наличии / под заказ» в буквальном
смысле («есть на складе прямо сейчас») здесь неприменим и создаёт у клиента ложные
ожидания о моментальной отгрузке.

Переопределяю смысл поля: `availability` показывает не физический склад, а то,
**продаёт ли поставщик эту позицию сейчас**:
- `'available'` (значение по умолчанию для всех новых карточек) — позиция есть в
  номенклатуре поставщика, по ней можно обращаться к менеджеру. Бейдж на фронте:
  **«Под заказ»** (не «в наличии» — чтобы не подразумевать мгновенную отгрузку).
- `'unavailable'` — поставщик снял позицию с производства/поставки. Бейдж:
  **«Нет в поставке»**. Карточка при этом может оставаться на сайте (информационно/архивно);
  как показывать призыв к действию для такой позиции — решение чата «Фронтенд», не
  блокируется здесь.

> **Примечание (2026-08-31).** Формы заявки на сайте больше нет (юридическое
> решение, см. `architecture.md`). Призыв к действию в карточке товара — простая
> ссылка на `/contacts`, без сбора данных. Значение `deliveryTime`
> `"уточняется по заявке"` сохраняется как есть — «заявка» здесь означает
> обращение клиента к менеджеру, а не веб-форму.

Итог: бейдж сохраняется (по брифу дизайна он нужен), но получает смысл, который не
противоречит бизнес-модели.

### 2.3 Сверка со расширенной номенклатурой

Номенклатура шире, чем спецтехника: промышленное оборудование, газоанализаторы, КИП,
лабораторное оборудование. Схема (раздел 1) проверена на применимость:
- `specs` как гибкая таблица «параметр/значение» подходит под любой набор характеристик
  (диапазон измерения, класс точности и т.п.) без изменения схемы.
- **Открытый вопрос, оставлен как есть**: для КИП/газоанализаторов/лаб. оборудования
  часто значимы сертификат соответствия / свидетельство о поверке / класс точности.
  Отдельного поля под это не завожу — такие данные ложатся в `specs` как обычная строка,
  либо (если это отдельный документ, а не характеристика) — в новое поле `documents`.
  Выделение отдельного поля `certification` в `specs` — решение по факту, если практика
  фронта покажет необходимость выводить это отдельным бейджем.

## 3. Комплектация и документы — структура для вкладок

- **`package`** (вкладка «Комплектация») — простой список строк, без вложенной структуры:
  каждый пункт того, что физически входит в поставку (например: «Основной блок»,
  «Кабель питания», «Инструкция на русском»). Не завожу отдельный тип под пункт
  комплектации — это не оправдано, пока нет данных, где элементу комплекта нужны
  собственные атрибуты (см. `Coding Rules.md`: без абстракций под гипотетические сценарии).
- **`documents`** (вкладка «Документы», включая кнопку «Скачать PDF») — список
  `{ title, url }`. Один и тот же тип покрывает и PDF-паспорт оборудования, и возможные
  сертификаты/инструкции — не завожу отдельное поле `pdfPassportUrl` только под паспорт,
  чтобы не плодить похожие поля под каждый вид документа. Хранение файлов — Vercel Blob,
  путь `docs/{productId}/{filename}.pdf` (зафиксировано в `Tech_Stack.md`); в `documents`
  попадает готовая Blob-ссылка, саму загрузку файлов делает не этот чат.

## 4. `Product` vs `ProductDraft` — подтверждение решения

Подтверждаю как финальное (решение уже принято в `Project_Structure.md`, здесь —
фиксация на стороне схемы данных, чтобы не разошлось с кодом):

- **`Product`** (раздел 1) — публичный тип, именно он используется в компонентах
  (`components/features/product/*` и т.д.), уходит в клиентский код.
- **`ProductDraft`** — расширяет `Product` одним дополнительным полем `missingData: string[]`
  (список характеристик/полей, которые нужно уточнить у поставщика). Используется только
  внутри `lib/data/products.ts` как рабочая пометка при заполнении карточек. **Не входит
  в `Product`** и не должен попадать в клиентский код/компоненты — так служебные
  редакционные заметки не утекают на фронт.

## 5. Открытые вопросы к следующему шагу

- Ожидается загрузка первых материалов от поставщика (прайс-лист/спецификация) — без
  них раздел «Наполнение реальными товарами» не может быть начат.
- Список категорий (`lib/data/categories.ts`) — фиксируется по мере поступления товаров
  разных типов; на этот момент ни одна категория в этом чате не согласована.
- Список производителей (`lib/data/manufacturers.ts`, на который ссылается `manufacturer`)
  — наполняется по мере поступления данных, тем же чатом (см. `Architecture.md`).
