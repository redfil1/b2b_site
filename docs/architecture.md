## 1. Источник данных каталога

По ТЗ отдельного бэкенда нет ("формы обрабатываются через API routes, без отдельного бэкенда"), сайт — каталог-витрина. Поэтому: **данные каталога — локальные** (JSON/TS-файлы в репозитории, без сети и без слоя-абстракции под "REST/CMS на будущее").

`lib/data/products.ts` и `lib/data/categories.ts` — функции, которые читают и отдают локальные данные (`getCategories()`, `getProduct(slug)`), без прослойки под гипотетическую смену источника. Так короче путь при дебаге: разработчик открывает файл и сразу видит, откуда данные.

Если в будущем понадобится CMS — меняем содержимое этих файлов отдельным решением; закладывать абстракцию заранее не нужно (правило проекта "не использовать сложные абстракции без необходимости").

**Влияет на чат "Карточки"**: наполнить `lib/data/products.ts` реальными товарами (структура — в `types/product.ts`), фото — в `public/` или во внешнем хранилище (домен — в `next.config.js`).

## 2. Структура страниц и роутинг (App Router)

```
/                          — главная
/catalog                   — каталог (список категорий или всех товаров + фильтры)
/catalog/[category]        — товары внутри категории
/catalog/[category]/[slug] — карточка товара
/search                    — результаты поиска
/manufacturers             — список производителей
/services                  — услуги
/company                   — о компании
/contacts                  — контакты
/delivery                  — доставка и оплата
/request                   — заявка / оформление заказа (B2B — не корзина с оплатой онлайн)
/request/success           — экран благодарности после отправки заявки
/legal/[doc]                — политика конфиденциальности, оферта и т.п.
```

Решения:
- **Двухуровневый каталог `[category]/[slug]`**, а не плоский `/product/[slug]`: у спецтехники всегда есть категория (экскаваторы, погрузчики и т.д.), это отражается в URL и упрощает SEO/хлебные крошки. Категория — обязательное поле у товара в `types/product.ts`.
- **`/request` вместо `/cart`**: B2B-продажа — не "корзина с оплатой", а форма заявки (возможно, с несколькими позициями). Состав полей — предмет чата "Заявка"; здесь фиксируется только URL и то, что это отдельный раздел, не вложенный в каталог.
- Отдельный `/search`, а не модалка/дровер — так поиск получает свой URL, шарится и индексируется. **Инлайн-поиск в шапке/каталоге** (если появится по брифу дизайна) реализуется как форма, которая по сабмиту ведёт на `/search?q=...` — отдельного клиентского полнотекстового фильтра не заводим, чтобы не было двух реализаций поиска.
- **`/manufacturers` и `/services` — заводим как отдельные разделы**, по аналогии с `/company`/`/delivery`. `/services` — статичная страница, данные прямо в `page.tsx` или в `lib/constants/`, отдельной модели не требует. `/manufacturers` — список с логотипами, это уже структурированные данные → `lib/data/manufacturers.ts`, тем же локальным паттерном, что `products.ts`/`categories.ts` (см. п.1): без сети, без абстракции под источник.

**Влияет на чат "Заявка"**: маршрут `/request`, серверная сторона отправки формы — `app/api/request/route.ts` (контракт см. в `API.md`).

**Влияет на чат "Фронт"/"Карточки"**: разбивка на файлы — см. `Project Structure.md`. Наполнение `lib/data/manufacturers.ts` реальными производителями — зона чата "Карточки" (по аналогии с товарами/категориями).
