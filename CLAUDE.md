# CLAUDE.md — рабочие правила для Claude Code

Этот файл — точка входа для Claude Code в проект. Он не заменяет документы в `docs/`,
а только задаёт правила работы с ними и даёт карту, что где искать. Всё содержательное
(структура полей, конкретные значения, формулировки) — в самих документах `docs/`, не здесь.

## О проекте
B2B интернет-магазин промышленного и специализированного оборудования (газоанализаторы,
КИП, лабораторное оборудование, спецтехника), импортируемого из Китая. Склада в РФ нет —
всё под заказ. Клиенты — юридические лица, оплаты на сайте нет. Флоу: клиент выбирает товар
→ связывается с менеджером напрямую (телефон/email, указанные на сайте) → менеджер вручную
готовит КП и согласовывает заказ у поставщика. Сбора персональных данных на сайте нет: форма
заявки и автоматизация «заявка → PDF КП → email менеджеру» убраны юридическим решением
от 2026-08-31 (152-ФЗ — не становиться оператором персональных данных). Личный кабинет
и авторизация на этом этапе не реализуются.

## Стек и ключевые ограничения
- Next.js (App Router) + TypeScript + Tailwind CSS, деплой на Vercel (автодеплой из GitHub,
  `main` → Production, остальные ветки → Preview)
- Отдельного бэкенда нет — вся серверная логика внутри route handler'ов Next.js
- Каталог — локальные TS/JSON-данные в `lib/data/`, без CMS и без сетевого слоя
- «Живых» сетевых сценариев на сайте нет — это статичная каталог-витрина. Форма заявки
  (`POST /api/request`) и фоновая генерация КП (`after()` + Vercel Blob) отменены
  юридическим решением от 2026-08-31; `docs/api.md` и `docs/commercial-offer.md` помечены
  как устаревшие
- TypeScript strict mode, ESLint + Prettier — единый конфиг репозитория
- Node.js версия зафиксирована в `package.json` (`engines`)
- Алиас путей `@/*` → `src/*`

## Правила кода — чего НЕ делать
- **Не вводить абстракции "про запас"**: ни слой над источником каталожных данных (на случай
  будущей CMS), ни обобщённую "сетевую обёртку". Решаем текущую задачу, не гипотетическую
  будущую.
- **Не заводить дублирующие типы.** `Product`, `Category` объявлены один раз
  в `types/` и импортируются везде — новый интерфейс с тем же смыслом в другом месте не создавать.
  (`RequestPayload` / `types/request.ts` относятся к отменённой форме заявки — не использовать.)
- `components/ui/*` не обращается к `lib/data` и не содержит бизнес-логики — только пропсы
  и вёрстка. Работа с данными — в `components/features/*` или `page.tsx`.
- Не использовать `/cart` и `/request` — оплаты и сбора заявок на сайте нет. Призыв к
  действию (шапка, карточка товара) — простая ссылка на `/contacts`, без `tel:`/`mailto:`
  и без форм сбора данных.
- Не менять роутинг, структуру папок или контракты API относительно того, что зафиксировано
  в `docs/`, без явного обновления соответствующего документа.
- Не реализовывать личный кабинет / авторизацию — отложено за пределы этого этапа.
- Изображения — только через `next/image`; домены — в `next.config.js` (`images.remotePatterns`).
- Цена товара нигде не берётся из `Product` — в типе её нет. Цену и КП менеджер готовит
  вручную вне сайта; автогенерации PDF КП в проекте больше нет (юридическое решение
  от 2026-08-31).
- Не хардкодить подписи статуса товара в компонентах — брать из
  `PRODUCT_AVAILABILITY_LABELS` (`types/product.ts`).
- Анимации — только Tailwind `transition`/CSS (fade/translate/blur/scale), без сторонних
  анимационных библиотек (Framer Motion и т.п.).
- Naming: роуты и файлы — `kebab-case`, компоненты — `PascalCase`, хуки — `useCamelCase`.
- SEO/метаданные — только через встроенный `generateMetadata`, отдельную библиотеку не добавлять.
- Комментарии обязательны на нетривиальных участках логики (см. `docs/coding-rules.md`).
  Прежние обязательные точки (валидация формы заявки, генерация PDF КП, загрузка в Vercel
  Blob) отпали вместе с отменой формы заявки.

## Порядок работы
1. Перед написанием кода в любой области — прочитать соответствующий файл `docs/` из таблицы
   выше целиком, не фрагментом.
2. Если решения в `docs/` не хватает для конкретной технической детали — не додумывать и не
   выбирать самостоятельно между вариантами, а спросить пользователя.
3. Архитектурные решения принимаются только в `docs/`. Claude Code — исполнитель зафиксированного,
   не самостоятельный архитектор: не менять контракт API, схему `Product`, роутинг или дизайн-токены
   по собственной инициативе.
4. Если при реализации всплывает противоречие между файлами `docs/` (не должно — последний аудит
   подтвердил согласованность, но новые правки могли внести расхождение) — не выбирать сторону
   самостоятельно, сообщить пользователю.
5. Любое новое архитектурное решение, принятое по ходу разработки (в диалоге с пользователем),
   сначала фиксируется в соответствующем `docs/*.md`, и только потом попадает в код.
